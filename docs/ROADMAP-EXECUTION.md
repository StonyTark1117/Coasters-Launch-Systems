# Roadmap execution guide

Updated 2026-11-22. [ROADMAP](../ROADMAP.md) owns scope and acceptance;
[CURRENT-WORK](CURRENT-WORK.md) owns assignments. These steps are procedures,
not extra gates. Apply [validation policy](VALIDATION-POLICY.md) and
[private run preparation](RUN-PREPARATION.md) to actual checks.

## Document responsibilities

Use Fourth Dimension's [guide responsibilities](<../../Coasters: Fourth Dimension/docs/roadmap/README.md#document-responsibilities>)
as the maintenance pattern. Each fact has one authoritative home:

| File | Responsibility |
| --- | --- |
| [ROADMAP](../ROADMAP.md) | Permanent LS IDs, scope, real prerequisites, package status and acceptance. |
| [CURRENT-WORK](CURRENT-WORK.md) | Active owners, precise remaining claims, next actions and evidence links. Future rows are planning inventory, not active assignments. |
| This guide | Ordered procedures, inputs and handoffs; no duplicate live owner/status fields. |
| [PLAN](../PLAN.md), mechanism docs and [dependency review](DEPENDENCY-REVIEW-2026-11-22.md) | Design contracts and dated decisions. Dependency availability is not acceptance. |

| [AGENTS](../AGENTS.md), [validation policy](VALIDATION-POLICY.md), [run guide](RUN-PREPARATION.md) | Operating rules, evidence reuse/stopping and executable setup/input procedure. |

When requirements change, update the canonical package and its guide together.
Check IDs, links, actual prerequisites and release allocation; do not clone a
case into multiple trackers. A retained execution card never reopens a closed
package. Read the assigned card's relevant inputs first, then follow evidence
for its claim rather than rereading the entire checkpoint history.
Documentation-only work needs document inspection, not a Minecraft build/run.

## Resume and handoff

1. Inspect branch, HEAD and dirty files; retain the assigned checkout. Read the
   current owner/case and latest accepted evidence or diagnosed failure. Confirm
   actual prerequisites: an unrelated unfinished gate or higher stage number
   alone does not block ready work. A busy sibling owner does not expand scope.
2. For a retained runtime, read its owned run.json and verify live units,
   PID/cgroup/window, endpoint, connection and game directory. Read the latest
   input record and observed result before acting. If stopped, reuse the saved
   world/configuration only when the named remaining check needs a run. Do not
   launch merely to reconstruct context or repeat solved input discovery.
3. Name the next unresolved criterion and expected readback. Continue compatible
   steps through the complete assignment; a guide step is not a new LS ID,
   mandatory run, approval or reason to stop after a successful partial result.
4. Shared persistence, provider authority, native mass and rider interfaces have
   one coordinated implementation owner at a time. Dependents consume the
   integrated revision and accepted contract. Stable dimensions/specifications
   can unblock independent models/docs while mechanics continues. This source
   coordination does not prohibit parallel private clients on separate resources.
5. At handoff, record branch/path/HEAD/dirty files, integrated contract and exact
   artifact/profile, accepted evidence, precise remaining claim, and next action.
   For a run include world/root, owner, display, endpoint, units, last successful
   target/action/readback and shutdown status. Record body UUID/local target and
   timestamp when moving-body targeting was solved; old world coordinates are
   historical after motion. Keep this in the existing case/evidence/run record,
   without inventing another mandatory manifest.

Routine closure needs evidence and the owning package/current entry updated;
it does not need another review or permission round. Parent gates reconcile
accepted child outcomes and check only a genuinely missing interaction. Stop
owned runtimes on completion unless a continuing owner explicitly accepts them.

## Shared interface handoffs

For new or changed shared motion/boarding/authority interfaces, bring the
required occupied client proof forward before dependent mechanics consumes
them. Demonstrate the relevant normal configuration/boarding, motion, stop or
capture, unload and restored control; use a second real client when the changed
contract includes synchronization. Native checks still cover force/ownership
invariants. Functional geometry and controls must work; decorative refinement
may follow. Reuse that same evidence in later player acceptance. This schedules
existing criteria early; it adds no retrospective run to a closed package and
does not replace separate survival-construction claims.

Reference: FD's [shared-contract handoff](<../../Coasters: Fourth Dimension/docs/VALIDATION-POLICY.md#shared-contract-client-handoff>).

   [preparation evidence](evidence/workflow-refresh-20261115.md). Both profiles

   separately, then record the coherent release baseline and deferred candidates.
3. Execute [the FD handoff](FOURTH-DIMENSION-HANDOFF.md): registration, allowed

   Arrow/independent-carrier interaction, including affected veto/recovery.
   Later packages reuse this evidence rather than repeating it.
5. Hand off exact artifacts, adapter/provider identity, supported operations,
   exclusions, evidence and shutdown. Compilation alone does not qualify a bridge.

## 0.1: LS101–LS106

Read [local control](LOCAL-CONTROLLER.md), [circuits](CIRCUITS.md),
[stations](STATIONS.md), [fin clamps](FIN-CLAMPS.md) and
[receiver recovery](RECEIVER-RECOVERY.md). Reuse dev.69–72 Span Tool,
floor-anchor, controller and Ponder evidence. Finish normal survival-built
ordinary, Arrow and Free Spin rides: repeated departure/travel/whole-train stop,
native capture, exit/boarding and fresh dispatch. Setup commands do not prove
construction. Ordinary work can proceed without FD; current-FD rides need LS004.

Then close the actual missing real-client lifecycle claims. Existing
connection/late-join and native fault evidence remain usable; review changed
contracts before carrying older-profile evidence into the release baseline.

## 0.2: LS201–LS205

Use [linear motors](LINEAR-MOTORS.md), [skid brakes](SKID-BRAKES.md) and
dev.54–61. Reconcile accepted signed motion, distinct LSM/LIM losses, reserves,
tail clearance, thermal derating and original-family rotation. Finish missing
player, rollback/profile and lifecycle criteria. Do not advertise unimplemented
linear section transfers or invent them as a new implicit acceptance condition.

## 0.3–0.4: LS301–LS403

Use [cable mechanics](CABLE-MECHANICS.md) and restart/interruption records through
dev.62. Inspect current FD body restoration before treating the old schema-4
Arrow release limitation as a continuing upstream blocker. Reproduce only the
relevant missing behavior after the bridge changes.

Finish physical guide/catch/release/return/service with finite flywheel,
hydraulic and pneumatic stores. Retain distinct pressure and power-loss behavior;
another addon's launch label does not prove these mechanics. Match recipes,
models and Ponder to controls. Combine earlier acceptance with remaining
occupied/service evidence to close 0.4 and select its packaged baseline.

## 0.5: LS501–LS504

Use FD specifications, current source and the body-variant manifest linked in
the handoff. Specify drive surfaces/plates/fins/sockets and swept envelopes.
Start with fixed-seat/spinning contracts, then posture/retention and specialized
cycles. Preserve native passenger mass, rotation, yaw, locks and restraints.
Deliver a finite certificate table with functioning eligible combinations,
evidenced exclusions and artifact identities. Reuse unchanged appearance/body
contracts; FD 1.4 vehicles need a separate later allocation.

## 0.6 and optional adapters

LS601/LS602 consume FD's `RideLocalOperations`, `RideAuthority` and accepted
1.2 manifest. Define how LS stopping/equipment leases consume route permission
before adding callbacks/UI. Prove conflicting dispatch denial and recovery on
the actual bounded Arrow route; this does not qualify general routing.

LS801–LS807 follow [optional integrations](OPTIONAL-INTEGRATIONS.md).
Prioritize Engineered's existing seam and Additions' new launch overlap, then
other force/appearance/presentation cases as assigned. Imported signals are
requests. Suppress competing force through a verified seam or reject the overlap.

## 0.9–1.0 reconciliation

LS901–LS904 consume cumulative certificate, gameplay, lifecycle and performance
evidence. Measure a disclosed representative workload, not an exhaustive
Cartesian matrix. Repair/retest only affected claims. LS1001 requires adopted
core gates and accurate optional support labels; publication follows readiness
as a separate action. Completion includes evidence and verified shutdown, or
an explicitly accepted live handoff to a named continuing owner.
